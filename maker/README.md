# ChineseBQB Maker

在现有表情包上改字。页面地址是 `/ChineseBQB/maker/`，和 Hugo 主站共用同一次 GitHub Pages 发布。图片、OCR、对比和导出都在浏览器里完成，没有账号，也没有上传图片的接口。

## 本地同时开两个服务

先启动 Hugo，让素材索引和原图可以从 `http://127.0.0.1:1313/ChineseBQB/` 访问：

```bash
python scripts/build_site.py serve
```

另开一个终端：

```bash
npm ci --prefix maker
npm run dev --prefix maker
```

打开 <http://localhost:5173/ChineseBQB/maker/>。Vite 把 `/ChineseBQB/catalog`、`/ChineseBQB/media` 和 `/ChineseBQB/thumbs` 代理到 Hugo。素材地址以 Hugo 站点为根，不会拼到 `/maker/media/`。

从分类页或搜索页预览一张图，点「制作同款」会打开 `maker/?src=media/<摘要>.<扩展名>`。GIF 支持时间轴分段改字；动画 WebP 只能改当前这一帧。

直接打开不带图片 `src` 的 Maker 页面时默认展开图库；从图片编辑入口进入时直接加载对应图片。图库展开时隐藏整个下方编辑区，选图或收起后恢复，顶部上传入口始终保留。图库每批显示 80 张，接近滚动底部时自动追加下一批，也可点击「加载更多」；搜索和分类显示完整匹配数量，切换筛选后从首批重新开始。瀑布流按已知图片比例定位，追加图片不移动之前的卡片。同一次会话里收起再打开图库会保留当前筛选、搜索词、已加载批次和滚动位置（选图自动收起后也一样）；这些状态只活在组件里，刷新页面就会回到默认，不做本地持久化。

## 首屏加载策略

`index.html` 自带纯 CSS 的首屏骨架：背景、品牌栏、预览和缩略图占位、加载状态、重新加载与返回图库链接都在内联样式里，不请求任何图片或字体，也不依赖应用样式表。生产构建由 `build/async-app-styles.ts` 把 Vite 提取的 CSS 改成带 `media="print"` + `onload` 的异步加载，并保留 `<noscript>` 回退；`main.tsx` 等到样式表报告的 ready 标记后才挂载 React，避免骨架提前消失或闪出未排版页面。

React 挂载后仍先显示图库卡片骨架和「正在读取素材索引…」。素材索引请求由 `afterFirstPaint` 在两次 `requestAnimationFrame` 之后启动，确保至少完成一次首屏绘制；第一次 setup 的回调会在 StrictMode 重放时取消，不会重复请求。缩略图请求期间卡片保留固定比例和轻量扫光动画，加载完成淡入，失败显示占位与提示；索引失败时显示原因和「重试」。

## 构建

和 GitHub Actions 的顺序一致。Hugo 会清空 `public-hugo/`，所以必须在 Hugo 构建之后再把 Vite 产物复制进去。

```bash
python -m unittest discover -s tests -p 'test_*.py' -v
npm run typecheck --prefix maker
npm run test --prefix maker
python scripts/build_site.py build
npm run build --prefix maker
mkdir -p public-hugo/maker
cp -R maker/dist/. public-hugo/maker/
python scripts/verify_site.py
python scripts/check_maker.py
```

`npm run test` 已经是单次运行，不要再加 `--run`。

## 怎么改一张图

1. 选择索引里的图，或上传本地 PNG / JPEG / WebP / GIF。GIF 默认一个片段覆盖整张动画；可定位到某帧后点「在此分段」，再分别改各段文字。动画 WebP 只能改当前这一帧。
   从图库选择时立即用已缓存的缩略图填入预览，后台下载原图、准备编辑像素；GIF 通过校验后即进入时间轴，帧像素在用到时才按原尺寸解码。原图未准备好时不能编辑或导出，OCR 不阻塞图片显示。快速切图会中断上一张原图下载，并忽略旧任务结果。
2. 选中图片后会自动识别一轮。GIF 会检查全部解码帧，只对像素完全相同的连续帧复用识别结果，相邻帧中同文且位置接近的文字合并成字幕条目。字幕区只留「字幕」标题、条数和「…」菜单；每条字幕一行，含时间定位按钮、整句输入、删除/恢复图标，时间微调收在行内「…」里（输入秒数后吸附帧边界），不再渲染逐字格子。
3. 每一段文字拆成一个字一格。改格子里的字，或点加号再加一格。纯色背景会自动盖上。
4. 格子会在短暂停顿后直接改到图上。删掉一格只模糊那一个字的位置；句首新增的字向左排列，句尾新增的字向右排列，没有改动的原字保持不动。例如把 `我从不失恋` 改成 `老娘从不失恋`，会在原来的「我」处画「娘」，再在左边加「老」，不会把「娘」追加到句尾。左侧留白不足时，新增前缀会整体缩窄。不是横排时才会盖住整行。
5. 单字位置是按整行估算的，不是模型返回的单字框。
6. 角点可以拖。撤销、重做和「还原原图」回放的是文字状态，每次都从原图像素重新合成。
7. 扳手下方的「修改前后对比」开关显示同一帧的原图和修改结果，可拖动中线或用方向键调整；对比层不进入导出。
8. 静态图最长边超过 1600 像素时会先缩小，作为编辑画布；导出不包含选框和手柄。

导出按钮旁有原生复选框「适配微信表情」，默认勾选；导出开始后复选框禁用，本次任务锁定开始时的选择。勾选时点「下载」会直接自动压缩并下载，所有图片都生成真正的 `image/gif` 文件，而不是只改扩展名。静态 PNG / JPEG / WebP / 单帧 GIF 把编辑画布当前像素作为单帧输入，不重新解码原文件，因此输入尺寸和像素与编辑画布一致；动态 GIF 仍从原始压缩文件懒解码，保留原动画时序和现有压缩策略。勾选分支统一复用同一套 Worker 与 `exportWechatSegmentedGif` 管线，严格小于 500,000 字节，无需选择档位或再次确认。取消勾选后点同一个「下载」按钮，按原图实际尺寸导出：静图恢复原格式 PNG / JPEG / WebP（单帧 GIF 可保持 GIF），动态 GIF 保留动画、原生尺寸、编辑后的字幕和各帧时序，不套用 240 长边缩图或 500,000 字节预算。下载后显示实际文件体积。

「下载」旁的「复制」会合成当前修改后的画面并写入剪贴板，不创建下载文件。复制采用浏览器通用的 PNG，保留透明背景；GIF 复制时间轴当前选中帧及其对应字幕，完整动画仍使用下载。勾选「适配微信表情」时复制图片的最长边为 240（小图不放大）；取消勾选时从原图恢复实际尺寸并映射文字。复制路径直接生成 PNG，不先编码整段 GIF，也不使用 GIF 的调色板或 500KB 体积预算。

复制和下载共用覆盖整个页面的合成进度面板，显示实际处理阶段和本阶段已完成数量，未知进度及最终交付阶段使用不定进度条，不按时间伪造百分比。合成过程中可以取消，背景编辑区暂时不可交互；写入剪贴板或交付下载后不再提供取消。成功以圆圈勾选动画提示，约 2.4 秒后淡出；失败使用错误动画和可操作的说明，保留到点击「知道了」，不会自动改为下载。减少动态效果的系统偏好会关闭动画。关闭面板后恢复原按钮的键盘焦点。

剪贴板写入需要 HTTPS（或本机安全环境）和用户点击许可；不支持或拒绝授权时显示失败提示。`clipboard.write` 在点击事件里立即调用，`ClipboardItem` 接收 Worker 返回的 PNG Promise，以保留 Safari 的用户手势授权；不会读取用户原有剪贴板。参见 [MDN Clipboard.write](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard/write) 和 [WebKit Async Clipboard API](https://webkit.org/blog/10855/async-clipboard-api/)。

勾选「适配微信表情」时，下载统一按原比例缩放至最长边 240 像素（小图不放大），不补正方形边、不裁切，优先 256 色调色板、动画完整帧率、无限循环；编辑预览和改字始终使用原图分辨率。静图同样保留透明像素，且只编码一帧，不添加视觉动画。照片缩图先用带抗混叠的 Lanczos 滤波，避免原 GIF 密集网点在浏览器直接缩放时变成大块摩尔纹；擦字在原分辨率完成，新增/替换文字在最终 240 长边的像素网格重新绘制，之后连同画面一起训练调色板。颜色匹配使用精确 RGB 距离，最多缓存 65,536 个颜色，避免 RGB565 查表额外合并相近的渐变色。不透明动画从全时间线取样生成稳定全局调色板，用透明差分复用相邻帧中未改变的像素；真实透明动画继续使用完整帧清除方式，避免残影。只有实际编码超过 500,000 字节才逐步调整颜色与帧率，优先保留 240 长边及字幕清晰度，最后才缩小尺寸。保留可见且确实改过字的字幕开始/结束、分段边界和首尾帧，合并延时保持总时长；未改动、已删除或已停用的识别结果不固定帧。同一组尺寸、颜色和帧计划只尝试一次。首个满足限制的结果作为已合格基线，最多再实测 4 次，在同一尺寸与帧计划下补回颜色，利用 160→128 等大步降档留下的体积余量；回补超限时保留基线，不下载超标文件。256 色首次已满足上限时不额外尝试降档。

取消「适配微信表情」时，导出仍会重新合成当前编辑，不是下载未经编辑的源文件。静态图导入时若最长边超过 1600 像素，编辑画布只是缩小后的预览；原图 Blob 仍保留完整像素，因此导出会重新解码原图，把擦字框、字体字号、描边和自由文字坐标按两个轴映射到原尺寸后重新合成，而不是把 1600 预览放大。JPEG / WebP / PNG 沿用原格式；浏览器不能编码该格式时回退 PNG，下载扩展名按实际 `Blob.type` 决定。单帧 GIF 可继续编码为 GIF。动态 GIF 从未编辑的原始压缩文件逐帧懒解码，在原生尺寸逐帧流式合成和编码，不保存整套原生 RGBA 帧；编辑器现有的 200 帧导入抽帧上限不变。

在画质基线确定后，不透明、240 长边的动画还会自动优化流畅度：锁定同一调色板、像素映射和字幕渲染，逐对实测透明差分、连续同色行填充和完整帧三种等价编码的字节成本，用动态规划选择更密的真实源帧。不能跨越字幕起止/分段边界，最大停帧不超过原方案，并按同一调色板下的时间加权重建误差检查不退步；重复画面不会被用来虚增帧数。新结果必须有更多帧且严格小于 500,000 字节，否则使用已经合格的原方案。搜索限定 200 帧、最多跨 8 个源帧，长延时拆帧和透明源保留原路径，避免无界计算。

导出在专用 Worker 中完成。勾选「适配微信表情」时，静态图只接收编辑画布的 `ImageData` 单帧，动态 GIF 解码原始压缩文件；两者都在原编辑尺寸擦字与合成，每帧只处理一次并缓存 240 长边的结果（最多 200 帧，RGBA 不超过约 46MB），各轮压缩复用这些结果。取消勾选时，Worker 接收原始 Blob 和编辑画布尺寸：静图重新解码原尺寸后在原生像素上合成一次；动态 GIF 保持惰性解码，合成一帧就交给编码器再读下一帧，不缓存整套原生 RGBA。两种模式都保留处理和压缩进度，可随时取消；取消、换图、页面关闭与出错都会结束 Worker，120 秒超时也会释放任务并允许重试。编辑中的原图、字幕和 `ImageData` 不会被压缩或更改。擦字使用与原先像素结果一致的滑动求和模糊，并跳过已删除文字的字色/描边分析。

导出为 GIF 不保证所有微信版本和所有发送入口都会按自定义表情处理，实际效果需以客户端为准。

2026-10-22 联网检索：聊天自定义表情与开放平台投稿口径不同，公开制作参考中的主图大小还存在按类别 100KB / 500KB 的差异（[制作规格参考](https://github.com/yizhi-chengzi/wechat-sticker-factory/blob/master/references/platform-spec.md)、[另一制作工具的基准](https://github.com/stylejinmu/sticker-kit#asset-specifications)）。本次未能读取[微信官方最新指引](https://sticker.weixin.qq.com/)，因此上述参数是本工具的保守聊天兼容默认值，不声称满足所有类别的商店上架审核；不将网上的「最多 24 帧」或固定时长建议当作已核实的微信限制。

GIF 的「删除原文」保留空目标字幕，在相应帧中局部修补已烧入像素的文字；「恢复原文」会撤回此条覆盖，不是重新画一遍原文字。每帧使用该帧 OCR 位置进行预览和导出。字幕整句替换会按目标字序整行重绘；静态图仍使用原有单字差分方式。识别、改字、删除、调整范围和分段均可撤销/重做；整段重识别一次提交，失败、取消或扫描期间开始编辑时保留原有编辑。切图、定位播放头和导出也会取消在途识别。识别进度显示已检查的解码帧数，复用同一个 OCR 引擎串行处理，不在历史中保存帧像素。

字幕范围采用半开帧区间，时间换算保留 GIF 的不等帧延时。如果原 GIF 超过 200 帧，导入时仍会均匀抽帧并提示，因此此处的「全部」指保留下来的解码帧，不能保证识别到导入阶段已被跳过的极短字幕。复杂背景的像素修补有限；OCR 误识别和位置变化较大时需在轨道中核对。此功能只支持 GIF，未增加视频导入。

## OCR、模型和隐私

锁定版本是 `@paddleocr/paddleocr-js@0.4.2`（Apache-2.0）。识别使用 PP-OCRv5 mobile 的检测和识别模型，每轮在独立的模块 Worker 中运行。

- 两份权重在 `maker/public/models/`，开发和 Pages 都从 `/ChineseBQB/maker/models/` 加载。识别不会请求 `paddle-model-ecology.bj.bcebos.com`。
- 这些文件是模型，不是用户的图片。本应用没有把图片发给 OCR 服务的接口。
- OCR 程序独立打包，脚本下载失败时最多尝试三次，重试地址绕过浏览器缓存的失败结果；后续点「重新识别」仍可发起新请求，无需刷新页面。构建时检查 OCR 不会成为主页面的静态依赖。
- 模型按引擎请求下载，公共模型保存在浏览器 Cache Storage 中；存储不可用时仍可直接下载识别，不缓存用户图片。WASM 通过同源 URL 交给浏览器加载，不在运行库配置中额外保留完整字节副本。
- 首屏仅浏览图库时不下载 OCR 引擎和模型。素材索引请求结束后，等用户点击或按键，再利用空闲时间预热；重复交互不会创建第二个 Worker。选图会直接开始识别，并复用已有的 Worker 和初始化任务。预热失败不打断浏览图库，选图时会重新尝试。预热完成后闲置 5 分钟、页面转入后台或离开页面时释放未使用的 Worker。
- 资源下载最多等待 90 秒。失败时显示原因并提供「重新识别」，重试不会被上一轮失败的任务堵住。
- Vite 会把 `onnxruntime-web` 的 WASM 放进 `/ChineseBQB/maker/assets/`。应用自行管理 Worker，使用 OffscreenCanvas 读取识别像素，不启用 SDK 内置的 CDN Worker。
- 构建插件把锁定版本 OpenCV 的初始内存从 128 MiB 降到 32 MiB，同时修改 JavaScript 分配值和内嵌 WASM 的内存导入下限，保留原来的增长上限。构建时检查内存契约、数据段范围和 WASM 有效性；升级依赖后格式改变会阻止构建，须重新评估。
- OCR 始终从编辑像素生成输入，最长边限制在 480–640 像素，并把识别框按两个轴映射回画布；不会重新读取原始大图。
- 识别时显示 5 个实际阶段的进度条和已用时间：准备图片、加载识别引擎、加载并初始化模型、识别文本、整理结果。进度表示已完成步骤，不估算耗时百分比；GIF 标明当前识别帧。切帧、切图或取消后，旧任务的进度不会覆盖新任务。
- 识别任务串行运行，切图后跳过过期任务。成功的引擎短期复用，失败、超时、离开页面或闲置到期后终止 Worker；取消时立即脱离旧消费者，旧推理结束后才供新图复用。检测与识字模型依次下载、初始化，源模型字节及时解除引用，后一个模型失败也会释放前一个会话。iPhone/iPad 及低内存设备默认使用 basic 图优化、关闭 CPU 内存池与形状内存缓存，检测最长边限为 480（只影响识别输入，不改变编辑和导出画质）。内存故障后终止旧 Worker，自动以此配置重试同一张图一次；取消、切图、隐藏或离开页面会阻止这次恢复。再次失败才显示手动重试。预热及单次识别各最多等待 180 秒。识别期间暂不允许导出，避免两种高内存操作叠加。
- 模型文件缺失或初始化失败时显示错误，仍可手工加字并导出。浏览器进程被系统终止不属于可捕获的 JavaScript 错误。

## 已知限制

- 只保证近水平、字距较整齐、背景接近纯色的单行中文。竖排、大倾斜、透视和复杂背景会标成需要确认或手动处理。
- 识别出的格子沿用原文字的大小和颜色。字号、颜色、描边和粗细只在「添加文字」后的手工文字上设置。新字用系统中文无衬线字体，不能还原原图字体。
- 导出时会把擦除框外的像素恢复成原图，避免抗锯齿改到旁边的字，所以新字可能被框裁切。
- GIF 在独立 Worker 中只校验元数据、体积、边长和帧数等上限，不分配任何 RGBA 像素；校验通过后把压缩后的原文件传回页面，Worker 立即结束。页面保留这份压缩数据，帧的 `ImageData` 按原尺寸懒解码，只维持两帧缓存和少量有界检查点，不会在主线程同时持有整套 RGBA 帧，也不把懒加载对象结构化克隆到别处。导入不再为了内存预算降低预览分辨率，只有导出时才缩小；超过 200 帧时仍均匀抽帧并累加原帧间隔，总时长保留。校验阶段拒绝超过 2000 帧或原始帧块累计超过 2 亿像素的动画。发生抽帧时提示会说明保留的帧数。
- GIF 最多分 20 段，分段以帧边界为准，当前帧属于新片段。分段继承原有文字，之后两段独立修改；分段及文字均支持撤销/重做。字幕不会自动跟踪移动物体，位置改变时需要再分段定位。导出按片段逐帧合成，用一个复用画布编码，保留处理后各帧间隔与动画总时长。动画 WebP 只处理当前帧。
- 没有生成式补背景。模糊或取样不能当成智能修复。
- 仓库里的表情包素材不因为开源就自动获得商用授权。
